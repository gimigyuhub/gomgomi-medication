# OCR과 약 이름 매칭 (`src/ocr-paddle.js`)

| 단계 | 입력 → 출력 |
|---|---|
| 사진 보정 | 사진 → 짧은 변이 1200px 미만이면 2배 확대 → CLAHE(8×8 구역별 대비 균일화) |
| 방향 판단 | 사진 → 글자 영역 검출, 세로로 긴 영역이 많으면 270°/90°, 아니면 0°/180°부터 시도 |
| 검출 | 사진(긴 변 최대 1600px) → `ch_PP-OCRv5_det_mobile.onnx` → 글자일 확률 지도 → 줄 영역(회전 사각형) |
| 인식 | 줄 이미지(높이 48px) → `korean_PP-OCRv5_rec_mobile.onnx` → 글자와 점수(0.5 미만은 버림) |
| 방향 선택 | 점수 0.85 이상이면 그 방향을 쓰고, 아니면 다른 방향과 비교 |
| 행 복원 | 같은 높이의 칸을 왼쪽부터 이어 줄 텍스트로 → 약 DB 매칭 |

모델 파일은 `assets/models/ocr/`에 있고(약 18MB, Apache-2.0), 실행기 onnxruntime-web 1.30.0은 jsDelivr에서 불러옵니다. 첫 사용 때 약 20MB를 내려받고 이후에는 브라우저 캐시를 씁니다. 사진은 기기 밖으로 나가지 않습니다.

PaddleOCR의 줄 방향 판별기(0°/180°)는 쓰지 않습니다. 실제 약봉투 사진에서 약 이름 세 줄을 거꾸로 판단해 뒤집어 읽었기 때문입니다.

실제 약봉투 사진 1장(옆으로 누운 휴대폰 사진, 약 6개)으로 비교한 결과:

| 엔진 | 약 DB 매칭 후 정답 | 잘못 채택 |
|---|---|---|
| Tesseract.js (이전) | 0/6 | 0 |
| Tesseract.js, 사진을 바로 돌린 뒤 | 3/6 | 1 |
| PP-OCRv5 브라우저 구현 (현재) | 6/6 (일치율 89~100%) | 0 |

같은 사진을 휴대폰 촬영에서 흔한 7가지 조건으로 망가뜨려(저해상도, 어두움, 그림자, 흐림, 강한 JPEG 압축, 빛 반사, 기울기) 앱 결과 칸(약 6개 × 이름·1회량·횟수·일수 = 24칸)을 채점하면, 원본을 포함한 8개 조건 합계 192칸 중 사진 보정 전 162칸, 보정 후 173칸이 맞았습니다. 저해상도는 16 → 24칸으로 크게 좋아졌고, 강한 JPEG 압축은 22 → 19칸으로 나빠졌으며, 흐림은 18칸 그대로였습니다.

사진 1장 결과라 더 많은 사진으로 확인이 필요합니다. 휴대폰에서의 처리 시간은 아직 측정하지 않았습니다(Mac 브라우저에서 모델을 받은 뒤 약 2초).

## 약 DB 매칭 정확도 (시뮬레이션)

약 DB의 제품 400개 이름에 OCR식 오류를 넣어 측정했습니다(로컬 Postgres 16). '이전'은 기존 방식인 medikr.kr 부분일치 검색(조건마다 40개)입니다.

| 질의 | 1순위 정답 | 3순위 이내 | 이전 3순위 이내 |
|---|---|---|---|
| 정확히 읽음(`mg` 표기) | 100% | 100% | 32.5% |
| 약봉투 한 줄 전체(이름+복용법) | 100% | 100% | 0% |
| 글자 1개 오인식 | 89.8% | 99.0% | 2.5% |
| 글자 2개 오인식 | 75.2% | 89.2% | 0% |
| 글자 1개 누락 | 78.8% | 92.5% | 30.0% |

질의 1줄당 약 10ms. 실제 Tesseract.js로 합성 약봉투(흐림·기울기·잡음·JPEG 압축)를 읽었을 때 OCR이 `mg`를 `08`로 읽어 기존 정규식 추출은 6개 중 0개, 약 DB 매칭은 6개 모두 맞혔습니다. 채택 기준 점수 0.55는 약이 아닌 약봉투 문장 30줄을 하나도 약으로 잘못 채택하지 않은 가장 낮은 값입니다. 실제 사진으로는 아직 측정하지 않았습니다. 원본 데이터: 건강보험심사평가원, 공공데이터포털(공공누리 제1유형, 출처표시).
